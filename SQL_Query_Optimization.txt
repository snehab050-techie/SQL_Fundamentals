SQL Query Optimization
-----------------------

SQL Query Optimization means improving a SQL query so that it executes faster and uses 
database resources efficiently.

Example:

Table - Employees 
With 10 million records

we have query:

SELECT *
FROM employees
WHERE emp_id = 1001;

Suppose this query take 12 seconds to execute. In a real production systems, this is a problem.
If the query is taking 12 seconds to execute per user, imagine for millions of users executing the same query at a time!!

Now we want to bring it from 12 seconds to 2 seconds without changing the expected result. That's Query optimization or Query performance tuning.

Why does a Query become slow?
------------------------------

1. Full table scan
2. Missing indexes
3. Incorrect / Inefficient indexes
4. Poor database design
5. Poor JOIN conditions
6. DB CPU & I/O pressure
7. Querying unnecessary columns
8. Scanning more rows at a time
9. Blocking / Locking issues
10. Large data volume

and many more!!

So optimization isn't simply - "Add an index"

What happens when we execute a query
---------------------------------------

Suppose our Java application executes:

SELECT name, salary
FROM employees
WHERE employee_id = 1001;

What happens inside the database?

Very roughly:

			 Java Application
      				 ↓
     				SQL
     				 ↓
				Database
       				 ↓
			     SQL Parser
       				 ↓
			   Query Optimizer
                                 ↓
                            Execution Plan
                                 ↓
                              Execution
                                 ↓
                              Result
                                 ↓
                          Java Application

The important part for us is 

                                SQL
                                 ↓
                              Optimizer
                                 ↓
                            Execution Plan



Execution Plan
--------------

An execution plan tells us:

"How does the database intend to execute this query?"

For example:

SELECT *
FROM employees
WHERE employee_id = 1001;

The database might decide:

Use index on employee_id
        ↓
Find employee_id = 1001
        ↓
Fetch the row

Another query might result in:

Full Table Scan
        ↓
Read 10 million rows
        ↓
Check employee_id for every row
        ↓
Return matching row

Obviously the second approach could be much slower.

Cost
-------

Cost is generally an optimizer's internal estimate of the relative resources required for a particular execution plan.

It can consider things such as:

CPU
disk I/O
number of rows
operations
access paths

Full Table Scan
-----------------

Imagine:

employees
---------
10 million rows

Query:

SELECT *
FROM employees
WHERE employee_id = 5000000;

Suppose there is no useful index on employee_id.

The database may need to check:

Row 1       → employee_id?
Row 2       → employee_id?
Row 3       → employee_id?
...
Row 5,000,000 → employee_id?
...
Row 10,000,000 → employee_id?

That's essentially:

FULL TABLE SCAN

Potentially expensive.

Index changes the game
----------------------------

Suppose we create:

CREATE INDEX idx_employee_id
ON employees(employee_id);

Now the database has a structure that helps locate the required row.

Conceptually:

Without Index

Table
 ↓
10 million rows
 ↓
Search everything

versus:

With Index

Index
 ↓
Find employee_id = 5000000
 ↓
Locate row
 ↓
Return data

Much less work in the appropriate situation.

"Should we create an index on every column?"
-------------------------------------------------

No.

Indexes have a cost.

When we perform:

INSERT
UPDATE
DELETE

the database may also need to maintain the indexes.

So too many indexes can cause:

SELECT
   ↓
Faster

BUT

INSERT/UPDATE/DELETE
   ↓
Potentially slower

And indexes also consume storage.

Therefore:

Indexes should be created based on actual query patterns and workload, not blindly on every column.

Analyzing SQL Query Optimization in Production Environments

API: /getEmployeeDetails

Normal response time:
500 ms

Current response time:
8 seconds

We shouldn't decide immediately: Database is slow.

Instead investigate.

API is slow
     ↓
Check application logs
     ↓
Identify SQL query
     ↓
Execute/analyze query
     ↓
Check execution plan
     ↓
Identify expensive operation
     ↓
Check indexes
     ↓
Check joins / filters
     ↓
Check row counts
     ↓
Check DB resource usage
     ↓
Optimize
     ↓
Test
     ↓
Deploy/change
     ↓
Monitor production

First analyze:
-------------

- existing indexes
- query frequency
- selectivity
- execution plan
- table size
- write workload
- DBA standards
- impact on other queries

----------------------------

Avoid SELECT * when we only need specific columns.

This can reduce:
- data transferred
- I/O
- memory usage
- network traffic
- application processing

-----------------------------

Another major issue: Functions on columns

Consider:

SELECT *
FROM employees
WHERE UPPER(name) = 'SNEHA';

Depending on the database and index design, applying a function to the column can prevent normal index usage.

------------------------------

JOIN optimization

Suppose:

SELECT e.name, d.department_name
FROM employees e
JOIN departments d
ON e.department_id = d.department_id;

You need to investigate things like:
Is department_id indexed?
Are we joining huge tables?
How many rows are being joined?
Is the JOIN condition correct?
Are unnecessary rows being joined?

A bad JOIN can cause a huge amount of work.

For example:
1 million employees
       x
100,000 department records

If the query is poorly constructed, the amount of processing can explode.

What is a Query Execution Plan actually showing us?

We'll commonly encounter operations such as:

Table Scan / Full Table Scan

Read a large portion/all of the table

Potentially expensive.

Index Scan
Read many entries from an index
Can be appropriate when many rows are required.

Index Seek
Conceptually:
Go directly to matching index entries
Often efficient for selective lookups.

selectivity - an important optimization concept
-------------------------

Suppose we have:
100 million rows

Column:
GENDER

Values:
MALE
FEMALE

If our query:
WHERE gender = 'MALE'

we might get 50 million rows.

The filter isn't very selective.
But suppose:
WHERE employee_id = 12345

returns only:
1 row

That's highly selective.
Indexes are generally especially useful for selective conditions.

Interview question:
Selectivity indicates how effectively a condition reduces the number of rows that need to be processed.

How to check an Estimated Execution Plan in Oracle

SQL Query:

SELECT *
FROM employees
WHERE employee_id = 1003;

EXPLAIN PLAN FOR
SELECT *
FROM employees
WHERE employee_id = 1003;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);

--------------------------------------------------------------------------------
| Id | Operation         | Name            | Rows | Cost |
--------------------------------------------------------------------------------
|  0 | SELECT STATEMENT  |                 |    1 |  500 |
|  1 | TABLE ACCESS FULL | ITR_EVERIFY_DETL|    1 |  500 |
--------------------------------------------------------------------------------

TABLE ACCESS FULL

This means Oracle is doing a Full Table Scan.
